# AI adapters

Why Claude Code works today, what "support" actually means, and whether your assistant can be
supported later.

## The short version

| | |
|---|---|
| **Works today, automatically** | Claude Code |
| **Architecturally supported, adapter not written** | Codex, Cursor, Gemini CLI, GitHub Copilot, and others |
| **Works today, manually, with any assistant** | point it at the generated `CLAUDE.md` |

EOS generates one assistant instruction file: `CLAUDE.md`. That is the whole of the current
support, and this page exists so that nobody has to reverse-engineer that from a repository.

## The two layers, and why the distinction matters

This is the part worth understanding, because everything else follows from it.

**`.engos/` is the Engineering Standard.** The structure of engineering memory: what a decision
is, what a capability is, that a milestone's status derives from its capabilities rather than
being declared, that observations are triaged before they become decisions. It is identical for
every project, in every language, with every assistant. It is what EOS reads, validates and
projects.

**An assistant instruction file is an adapter.** A translation of that one standard into the
mechanism a particular tool reads at the start of a session. It says: *this repository keeps
engineering memory; here is where each kind lives; record a decision when you make one; file an
observation when you notice a gap; you may propose a decision and may not accept your own.*

```
                 .engos/  —  the Engineering Standard
                     (one definition, never per-assistant)
                              │
        ┌─────────────────┬───┴────────┬──────────────────┐
        ▼                 ▼            ▼                  ▼
    CLAUDE.md        [adapter]     [adapter]         [adapter]
   Claude Code         Codex         Cursor        Gemini CLI …
   ── written ──    ── not yet written ────────────────────────
```

**The standard does not change per assistant. Only the file it arrives in does.** That is the
entire adapter concept, and it is why adding a tool is a new adapter rather than a new model of
engineering memory — and why the memory your assistant maintains is portable between
assistants, because it was never shaped by one.

It is also why EOS declines to claim support it has not built. An adapter that does not exist
is a repository whose assistant silently does not maintain its memory, which is worse than a
tool that says "not yet".

## What "support" means, precisely

Three things, and they are worth separating because only the first is missing for other tools:

1. **Generation.** `eos connect` writes the instruction file your assistant reads, without you
   authoring it, and `eos upgrade` keeps it current as the standard evolves. *This is what
   exists only for Claude Code.*
2. **The standard itself.** Identical for every assistant — it is `.engos/` plus the taxonomy,
   and it is already in your repository regardless of which tool you use.
3. **Publishing.** Completely assistant-agnostic. `eos publish` reads three directories and
   sends them. It does not know or care what wrote the files.

So "Cursor is not supported" means precisely: *EOS will not write Cursor's instruction file for
you.* It does not mean Cursor cannot work with an EOS repository, and it does not mean your
engineering memory is in a Claude-specific format. It is not.

## Using EOS with any assistant today

The generated `CLAUDE.md` is plain markdown describing the standard. It contains nothing
Claude-specific beyond its filename. Two things work now:

**Point your assistant at it.** Most tools accept a file reference — "read CLAUDE.md and follow
it for this repository". At the start of a session, that is the same information the adapter
would deliver automatically.

**Or copy it to your tool's instruction path.** If your assistant reads a project-level
instruction file, copying `CLAUDE.md`'s contents into it works, with one caveat worth stating:
`eos upgrade` refreshes `CLAUDE.md` and knows nothing about your copy, so the two will drift
apart. That drift is exactly the problem an adapter exists to solve.

## Instruction mechanisms, per tool

Every assistant reads a project-level instruction file. **Which file is per-tool, and it
moves** — more than one of these has changed convention at least once, and a confidently wrong
filename in a document about honesty would be the worst possible error here.

So: the mechanisms below are what each tool documented at the time of writing, recorded to show
that the adapter work is small and concrete rather than speculative. **Verify against your
tool's current documentation before relying on any row.**

| Assistant | Project instruction mechanism | Adapter status |
|---|---|---|
| **Claude Code** | `CLAUDE.md` at the repository root | **Written.** Generated by `connect`, refreshed by `upgrade` |
| **Codex** | `AGENTS.md` at the repository root | Not written |
| **Cursor** | Rules files under `.cursor/rules/`; the older single-file `.cursorrules` is still honoured | Not written |
| **Gemini CLI** | `GEMINI.md` at the repository root | Not written |
| **GitHub Copilot** | `.github/copilot-instructions.md` | Not written |

**If a row is wrong for your tool, that is worth an issue** — and it is the single most useful
contribution this page can receive. Correcting a filename here is most of the work of the
adapter.

### Considerations that are not just a filename

Two differences are real and worth knowing before assuming every adapter is identical work:

**Some tools read instructions once per session; some read them per request.** That affects how
much an adapter can rely on the assistant remembering the standard mid-conversation, and may
mean a shorter, denser instruction file for some tools than for others.

**Some tools support multiple scoped rule files rather than one.** Where that is available, an
adapter could split the standard by concern — decisions, capabilities, journal — instead of
emitting one document. That is a better fit for the standard's shape, and it is a reason the
adapters may not all be the same file with a different name.

Neither changes `.engos/`. That is the point of the split.

## What an adapter has to do

Small, and specified by what already exists:

1. Emit the instruction content — one definition, in `eos_cli/installer.py`, rendered into the
   target tool's file and path.
2. Be refreshed by `eos upgrade`, which already regenerates EOS-owned artifacts in place and
   backs up a file that diverged.
3. Never write outside the paths it owns. `upgrade` does not touch `.engos/`, `docs/` or
   `discovery/`, and an adapter must not either.

If you use an assistant that is not Claude Code and want it supported, an issue naming your
tool and its current instruction mechanism is genuinely the useful contribution. There is no
model work involved.

## What will not change when adapters arrive

Worth stating, because "multi-assistant support" often means a format war:

- **Engineering memory stays identical.** Same taxonomy, same `.engos/`, same files. A
  repository connected with Claude Code today is exactly what a Cursor user gets tomorrow.
- **Nothing becomes assistant-specific.** There will be no `.engos/claude/` or Cursor-flavoured
  decision format. If that were ever needed, the standard would be wrong, not the adapter.
- **The gate stays.** An assistant may propose a decision; a human accepts it. That rule lives
  in the standard, so every adapter inherits it rather than re-implementing it.
